# Security and release gates

Ethereum Sepolia only: chain ID **11155111**. GLOW has no promised cash value, USD peg or redemption. No mainnet deployment, custody of player keys, seed collection or fabricated chain evidence is permitted.

## Invariants

- Verify the Supabase account and both AAL2 and an active verified TOTP factor on private server access. A connected wallet is not an authenticated account. The explicitly approved testnet registration auto-confirms email/password accounts: `email_confirmed_at` records activation, not verified inbox ownership. Never use a supplied email to promote a player, merge identities or recover someone else's account.
- Link wallets through a server-created SIWE message bound to account, address, domain, URI, chain, nonce and expiration. Verify the exact stored message, consume once transactionally and reject cross-account takeover.
- Enforce RLS for direct database access as well as API ownership. Privileged clients and credentials remain server-only. Never use caller-provided account IDs as identity.
- Validate addresses/checksums, nonzero recipients, exact `bigint` amounts, balances, chain, token and spender. Review recipient/amount before the player's own wallet confirmation. Submitted hashes are not confirmed payments.
- Verify canonical successful receipts, payer, contract, event, amount, stored round and confirmations independently. Deduplicate receipts even after account deletion.
- Trust no client victory, practice seed, inventory, storage or `postMessage` for rewards. Persist server-owned action state and versions; reject stale and replayed requests.
- Sign results with a separate restricted signer, never the owner's mint key. Bind chain, verifying contract, recipient, round, exact deposits/result and expiry. Contract settlement must be replay-safe and backed by a funded pool.
- Treat `NEXT_PUBLIC_*` as public. Never log or record passwords, tokens, QR enrollment secrets, session cookies or private keys. Authenticated browser traces/videos are disabled.

### Locally implemented settlement boundary

`settlement-payments.ts` checks Sepolia, exact destination/payer/calldata/value, a successful canonical receipt with two confirmations, the configured token/recycling pool, the expected entry or purchase event and its exact one-GLOW transfer. It checks the historical escrow round, class and purchase entitlement. Entry/purchase calldata binds a nonzero, wallet-unique payment ID and a deadline limited to 15 minutes by the contract. A hash alone grants nothing. Two confirmations are not finality; settlement rechecks canonical blocks.

Migration 003 records immutable public receipt identifiers, canonical payment time and randomness proofs, and atomically commits each purchase with its versioned action. It rejects cross-owner/class entry reuse, changed retries, deposit gaps, duplicate stock items and terminal changes. Migration 004 reserves one pending review per account and prevents unrelated actions until a paid purchase is reconciled. A lost browser journal can recover the same payment from its contract ID. Only an expired review proven unpaid at a canonical confirmed block can be released; this never returns a paid loss. Public payment tombstones survive account deletion. Migration 005 stores public signed results for retries. RLS and service-only permissions protect all three tables. **Migrations 001–008 are applied to the working hosted project. GLOW play is enabled for controlled owner acceptance, while public production play remains disabled.**

`prepare-settlement.ts` rechecks every ledger receipt, public randomness proof, persisted chance outcome and current escrow before building EIP-712 data. The message binds chain, contract, round, player, exact deposits, result and expiry. `issue-settlement.ts` verifies and saves a restricted service's signature before returning it, or reuses an unexpired saved result after revalidation. The browser independently checks signer, domain, recipient, deposits, deadline and unsettled escrow before requesting a transaction. No application-private-key fallback exists. The provisioned signer is enabled for controlled acceptance. `paidEconomyReady` remains false in production; the exact configured developer can use a server-only opt-in in development. Every review, recovery, entry, action and claim checks that account policy after authentication.

The isolated Supabase Edge Function candidate accepts only this Result protocol, through a constant-time server bearer check. It rejects browser origins, other signing methods, wrong domains/contracts, malformed/oversized/stalled requests, practice/demo/nonterminal state, mismatched class/deposits/recipients and invalid expiry. It independently reads a bounded terminal-state projection and confirmed chain configuration, then rechecks the canonical block and signing/ownership roles before returning a signature. The provider-held key is read only by the restricted function when signing is enabled. Tests use ephemeral unfunded keys. This is a restricted software signer, not hardware isolation or a second game backend. It still trusts the authoritative database and the application's receipt/beacon validation; compromised DB access or permanent action loss remains a release blocker. [Setup](SETUP.md#candidate-signing-and-randomness) records provisioning and recovery requirements.

### Randomness boundary

Entry commits its six encounter choices to the first quicknet beacon at least 60 seconds after the canonical payment block timestamp. Each paid NPC encounter uses the same rule for its own payment. The expected round cannot be selected by the browser or a relay. `drand-client` verifies the BLS signature against a fixed quicknet public key and scheme; SHA-256 plus rejection sampling derives bounded choices with chain/contract/round/wallet/transaction/action domain separation. Stored proofs and outcomes are rechecked before signing settlement. A missing or invalid proof blocks progression/settlement and preserves payment recovery; it never triggers a new draw.

This relies on the drand threshold network and authoritative Ethereum RPC data; it is not an onchain VRF or proof of all game execution. A long network outage can delay a paid round. The future-draw timing and service-recovery procedure require deployment review. Primary references: [drand specification](https://docs.drand.love/docs/specification/), [quicknet announcement](https://docs.drand.love/blog/2023/10/16/quicknet-is-live/) and [official client](https://github.com/drand/drand-client).

## Account data and retention

Migration 006 is applied to staging and the working service. Real private-account checks after promotion pass. Account export and deletion-request endpoints require an active account, current TOTP/AAL2 and database rate limiting. Deletion-request mutations also require the exact application Origin, strict bounded JSON and typed confirmation. Account IDs come only from the verified session. Service-only SQL functions and RLS prevent direct client invocation or cross-account access. Downloads whitelist personal/history fields and exclude authentication material; oversized exports fail rather than truncate.

Requesting deletion never performs Auth deletion or removes paid state. The operator must review any adventure/payment record against canonical settlement, recheck concurrent activity and preserve payment tombstones before a separately authorized erasure. Victory, defeat, a passed review deadline or a saved signature alone cannot clear the payment review requirement. Account erasure and backup retention remain staging-review work; no automatic fulfilment or notification is claimed.

Maintenance has no public API or schedule. Its dry-run default and fixed table/age allowlist keep payment records, private adventures, wallet links and active/recent rate limits out of cleanup. Tests use synthetic databases only. No hosted cleanup or account deletion is authorized by running a local test.

## Token and faucet milestone

All `/dev/*` requests require development mode, a valid server-only `DEVELOPER_USER_ID`, the exact matching verified Supabase account, an active Supabase account, AAL2 and an active verified TOTP factor. The proxy enforces this across the namespace, and each developer page repeats the check before loading tools or compiled artifacts. Guests, other accounts, missing configuration and production receive 404. Editable profile names, user metadata, query strings and wallet connections cannot grant developer access. Settings uses the same server check for the links and phone preview. The normal local practice route is `/adventure/test`; it does not show developer controls. Client-side practice remains untrusted and cannot pay GLOW.

The local `/dev/deploy` tool prepares a separate three-transaction plan: deploy `SLMSToken` with the connected wallet as owner, deploy `SLMSFaucet` for that token, then mint 5,000 GLOW directly to the faucet. No game contract, reward signer, owner allocation or player deposit is involved. The cap is 1,000,000 outstanding GLOW; owner mint authority remains, and self-burn reopens capacity. The faucet dispenses five tokens per wallet every 24 hours from its existing balance. These limits are per wallet, not proof of one person.

Deployment still requires the user's explicit plan authorization and individual MetaMask confirmations. Both contracts reject non-Sepolia construction. The tool checks the RPC/wallet chain, exact compiled input, payer, destination, zero ETH value, canonical block and two confirmations. Saved journals fail closed on changed builds, legacy plans and ambiguous submissions; do not clear them to retry an uncertain request. The independent verifier also checks deployed code, token identity/cap/owner, faucet token/amount/cooldown and the exact funding event. It saves only verified public addresses and leaves paid play/rewards disabled. Explorer source verification and a separate-wallet claim/transfer remain required evidence.

The separate `/dev/deploy/game` review and its `/prepare` and `/verify` endpoints repeat the owner restriction before reading artifacts. The server only prepares/verifies exact transaction data. Its browser sender rechecks both chains, the connected owner, the plan and current fees, and requires the user's explicit step authorization and MetaMask confirmation. An in-flight journal is saved before opening the wallet; ambiguous submissions stay locked for receipt reconciliation. The reviewed EIP-1559 fees are passed explicitly to the wallet. The endpoints take only a current plan fingerprint and public receipt hashes, never caller-selected roles, RPCs or paths. The shared CLI verifier checks exact creation/funding inputs, sender/nonce-derived address, runtime code outside compiler-declared immutable slots, EIP-712 domain, ownership, signer separation, paused/unused state, cap and exact reserve accounting. It rechecks all receipt/snapshot blocks after the reads. PASS is evidence at that confirmed block, not activation permission or chain finality. No sender code path writes release flags, installs keys or unpauses the game.

## Recovery, retention and known limits

Email password reset is unavailable because no public sender is configured. The reset page sends no request and states this limit. Authenticated password changes remain behind current TOTP; previously issued account callback links cannot bypass it. Lost-factor recovery needs an established support identity check. Global sign-out cannot invalidate an already issued access token before the provider's expiry. Direct database RLS checks the token's assurance claim; private APIs additionally check the current verified factor.

Private account export and cancellable deletion requests are implemented with migration 006, applied to both services and tested through the real private APIs. Bounded maintenance of expired challenges/rate-limit rows is implemented with a dry-run default. These features do not automatically erase accounts or payment evidence.

An eventual account deletion cascades private rows; public payment identifiers must remain to prevent reuse, and onchain records are immutable. Operator identity checks, unsettled-payment reconciliation, retention after restoration and a reviewed erasure procedure remain public-release work. A deletion request is not a completed erasure or an automatic refund.

The game needs a scoped CSP exception for MZ/Pixi shader compilation; account pages must not permit `unsafe-eval` in production. Finite reserves, rate limits and wallet limits bound rewards but do not prove resistance to automated legal play or multiple-wallet abuse.

See [the review](REVIEW.md) for current dependency findings and executed tests. Automated checks do not establish a professional security audit or complete accessibility conformance.
